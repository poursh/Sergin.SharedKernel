# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Sergin.SharedKernel is the building-block library for the **Sergin** platform — a .NET 10 modular monolith whose **MeterMinder** module is a Head-End System (HES) for smart electricity/gas/water meters. This repo holds the framework-level abstractions — `Domain`, `Application`, `Infrastructure`, `Presentation`, and host-bootstrap plumbing — shared by every Sergin module.

**This repo has zero dependencies on any other Sergin repo** and is not runnable on its own — it's a pure library. It's consumed as a **git submodule**:
- By [Sergin.MeterMinder](https://github.com/poursh/Sergin.MeterMinder) (the host repo) at `src/SharedKernel/`.
- By [Sergin.UserAccess](https://github.com/poursh/Sergin.UserAccess) (an embed-only module repo) at a matching relative path once UserAccess is itself embedded inside a host.

Because of this, changes here ripple into every module and host repo that pins a commit of this one. Treat public types/contracts (`ISerginModule`, `ISerginWebApiModule`, `ISerginWebUiModule`, `AggregateRoot`, `ICommand`/`IQuery`, `IEndpoint`) as a stable API surface — a breaking change here requires bumping the submodule pointer (and re-testing) in every consumer.

## Commands

```bash
dotnet build Sergin.SharedKernel.slnx
```

Requires the .NET 10 SDK. There is no project with its own `[Fact]`s in this repo — `Sergin.SharedKernel.IntegrationTests` provides shared integration-test *infrastructure* (`SerginWebApiFactory<TEntryPoint>`) consumed by a host repo's own test project, not a runnable test suite of its own.

## Critical build constraint

`Directory.Build.props` sets `TreatWarningsAsErrors=true`, `AnalysisMode=All`, and enables **SonarAnalyzer.CSharp** + `EnforceCodeStyleInBuild`. Any analyzer warning, style violation, or nullable warning **fails the build**. Nullable and implicit usings are enabled solution-wide. Write code that passes analysis cleanly the first time.

**Central Package Management is on.** `Directory.Packages.props` holds every package version as a `<PackageVersion>` entry, trimmed to just the packages this repo's 14 projects actually use (a subset of the full Sergin monorepo's package list — most host- and test-only packages, e.g. `Microsoft.EntityFrameworkCore.Design`, were dropped when this repo was extracted; `Testcontainers.PostgreSql`/`Microsoft.AspNetCore.Mvc.Testing`/`xunit` came back once `Sergin.SharedKernel.IntegrationTests` needed them; `MudBlazor` came back once `Sergin.SharedKernel.Presentation.Blazor` needed it). `PackageReference` items in `.csproj` files carry **no `Version` attribute** — add new packages version-less and add the matching `<PackageVersion>` entry here, keeping the list alphabetical.

## Project layering

- **`Sergin.SharedKernel.Domain`** — `AggregateRoot<TId>`, `Entity`, strongly-typed-ID conventions, `Ardalis.GuardClauses` (globally imported but **present-but-unused** — no constructor/factory in the consuming modules actually calls a guard clause yet), `RowVersion` (exists for optimistic concurrency, but no aggregate carries one today). Zero dependencies — the leaf of the whole Sergin dependency graph.
- **`Sergin.SharedKernel.Application`** — `ICommand`/`ICommandHandler`, `IQuery`/`IQueryHandler`, `IListQuery`/`IListQueryHandler`, `ListQueryResponse<T>`, `IUnitOfWork`, the MediatR pipeline behaviors (`PermissionCheckPipelineBehavior` enforces `[RequiredPermissionsAttribute]` against `IUserContext`; `ValidationPipelineBehavior` runs an optional FluentValidation `IValidator<TRequest>` if one is registered — order matters, permission check runs first), domain-event contracts (`IDomainEvent`, `IEventDispatcher` — dispatched by `EventDispatcherInterceptor` on EF `SaveChanges`, but **no consuming aggregate calls `Raise(...)` yet** — present-but-unused), time abstraction (`IDateTimeProvider`).
- **`Sergin.SharedKernel.Infrastructure`** — `SerginDbContext` base class, `IDbConnectionFactory` implementation, `EventDispatcherInterceptor`, `DefaultDateTimeProvider`. `RemoteForwardingHandler<TRequest, TResponse>` used to live here (`Infrastructure/Dispatching/`) but moved to `Sergin.SharedKernel.Presentation.Grpc` — see that project's entry below — alongside `IRemoteInvoker<TRequest, TResponse>`, the other half of the same dispatch contract; this project no longer references `Presentation.Grpc` or needs to.
- **`Sergin.SharedKernel.Infrastracture.Data`** *(sic — real project name, matches the typo)* — a near-empty leaf project; don't "fix" the typo by renaming without checking every consumer's `ProjectReference` path first.
- **`Sergin.SharedKernel.Infrastructure.Data.EFCore`** *(spelled correctly here — the inconsistency with the project above is real, not a documentation error)* — EF Core-specific building blocks: the `AddModuleDbContext<TContext, TIContext, TIUnitOfWork>` helper (wires a module's `DbContext`, schema, and per-schema migrations-history table) and `MigrateDbContextAsync<TContext>()`.
- **`Sergin.SharedKernel.Presentation`** — presentation-layer contracts shared by *every* front end, API or UI, not just the empty placeholder it used to be: `SerginProblem` (`StatusCode`/`Title`/`Detail`/`ErrorType`) and `SerginProblemFactory.Create(Error, ILocalizer)`, an `HttpContext`-free `Error` → `SerginProblem` mapping; plus `SerginApplicationOptions` (`ApplicationName`, bound from `Sergin:ApplicationName`, defaulting to `"Sergin Application"`, with the same `Validate(out string)` shape as `DevUserOptions`). It lives here rather than in a host bootstrap so both front ends can name the application identically — the Blazor app bar today, an OpenAPI document title if a Web API host returns. Both `Presentation.WebApi`'s `ApiProblemResults` and `Presentation.Blazor`'s `MudUiErrorPresenter` build on this, so API and UI render identical error text for the same `Error.Code`.
- **`Sergin.SharedKernel.Presentation.WebApi`** — `IEndpoint` (minimal-API endpoint contract), `ErrorOr` result-to-`ProblemDetails` mapping (`ToApiResult()`), `ApiProblemResults` (now a thin wrapper over `SerginProblemFactory` above). It still references `Sergin.SharedKernel.Application` — not for a dispatcher (there is no presentation-agnostic sender anymore; see Cross-cutting conventions below), but because `ListQueryRequestModel.cs` needs `ListQuery<T>`/`IListQuery<T>` from there to build a closed list query for a list endpoint. A WebApi endpoint injects `ISender` directly, the same as any other MediatR consumer.
- **`Sergin.SharedKernel.Presentation.Grpc`** — shared contract types for the dual-mode (MediatR/gRPC) dispatch mechanism: `IRemoteInvoker<TRequest, TResponse>` (the client-side "one interface per feature" stub a module implements to send a request over gRPC instead of in-process — still ends in `ISender.Send` on the server side, never a second entry point into Application), `RemoteForwardingHandler<TRequest, TResponse>` (`Dispatching/`, alongside `IRemoteInvoker` — moved here from `Infrastructure`) — wraps a module's `IRemoteInvoker<TRequest, TResponse>` as a real MediatR `IRequestHandler<TRequest, ErrorOr<TResponse>>`, so a Remote-configured module's requests flow through the same `ISender.Send` pipeline (and therefore the same `PermissionCheckPipelineBehavior`/`ValidationPipelineBehavior`) a Local module's real handler would, pure forwarding with no logic of its own — the generated `ErrorReply`/`ProtoErrorType` types compiled from `Protos/error.proto` (numerically aligned 1:1 with `ErrorOr.ErrorType`), and `ErrorReplyExtensions` (`Error.ToErrorReply()` / `ErrorReply.ToErrorOr<T>()`). A module's own `.Presentation.Grpc.Contracts` project (e.g. DeviceManagement's, in the `Sergin.MeterMinder` host repo) imports this project's `error.proto` and references this project's compiled types rather than redeclaring them; its `.Presentation.Grpc.Client` project references this project directly for `RemoteForwardingHandler`/`IRemoteInvoker` when wiring `AddRemoteServices`. **Live-but-unhosted today**: no running host passes a module as a `remoteModules` entry to `AddSerginCore` — see the `Hosts` entry below (`AddSerginCore`'s `localModules`/`remoteModules` split) and the `Sergin.MeterMinder` host repo's own CLAUDE.md.
- **`Sergin.SharedKernel.Presentation.Blazor`** (`Microsoft.NET.Sdk.Razor`) — the shared Blazor kit every module's UI slice builds on, registered as a unit via `AddSerginBlazorKit()`: MudBlazor services, `IUiErrorPresenter`/`MudUiErrorPresenter` (see Cross-cutting conventions below), `IUiThemeStore`/`LocalStorageThemeStore` (scoped rather than singleton because it depends on `IJSRuntime`, which in Blazor Server is per-circuit), and **`ISerginDispatcher`/`ScopedSerginDispatcher`** (registered singleton); plus `SerginUiModuleCatalog` (collects every `ISerginWebUiModule`'s `UiAssembly` and `NavItems` for the host to route and render), the home slot (`SerginHomePage`/`SerginHome`/`SerginHomeBuilder`/`SerginWelcome` — see below), and the shared shell components (`SerginMainLayout`, `SerginNavMenu`, `SerginProblemPanel`). **`ISerginDispatcher`/`ScopedSerginDispatcher` live here again, in `Dispatching/` (`ISerginDispatcher.cs`, `ScopedSerginDispatcher.cs`) — Blazor-only, not presentation-agnostic.** This reverses the `2026-08-22` move that had relocated the dispatcher (then named `ISerginSender`/`RoutingSerginSender`, and `ISerginUiDispatcher`/`RoutingSerginUiDispatcher` before that rename) out to `Sergin.SharedKernel.Application/Dispatching`/`Sergin.SharedKernel.Infrastructure/Dispatching` and wired its registration into `AddSerginCore` for every host. `ScopedSerginDispatcher.SendAsync` still opens one fresh `IServiceScope` per call — the SignalR-circuit-lifetime problem that motivated the type in the first place hasn't gone away — but it no longer pre-checks `[RequiredPermissions]` and no longer branches `Local`/`Remote` itself: both are now purely `PermissionCheckPipelineBehavior`'s job inside the MediatR pipeline, and that pipeline covers a Remote module's calls too, not just Local ones, via `RemoteForwardingHandler` (`Sergin.SharedKernel.Presentation.Grpc/Dispatching`, see that project's entry above). What still lives here regardless is `SerginDispatcherExtensions.SendListAsync` (`Presentation.Blazor/Dispatching/SerginDispatcherExtensions.cs`), a thin UI-only helper: list queries have no dedicated command type, so it builds the shared generic `ListQuery<TItem>` on the caller's behalf and documents the `pageIndex` 1-based vs. MudBlazor `TableState.Page` 0-based mismatch — genuinely Blazor-specific either way.
  - **The home slot.** This library owns the site root. `SerginHomePage` (`@page "/"`) renders whatever `SerginHome.ComponentType` points at through `<DynamicComponent>`; `SerginHomeBuilder` is what `AddSerginBlazorApp`'s `configureHome` callback configures, defaulting to `SerginWelcome` under a `("Home", "/", …, Order: 0)` nav entry. A consuming host therefore gets a working `/` without writing a page, and **must not declare an `@page "/"` of its own** — supplying a custom root is what `UseComponent<T>()` is for, and a second `"/"` template makes the routes ambiguous. Four deliberate shapes. This assembly is added to `SerginUiModuleCatalog.RoutableAssemblies` so the route reaches **both** consumers — the host bootstrap's `AddAdditionalAssemblies(...)` for the server-side endpoint and a host's `Routes.razor` for `Router.AdditionalAssemblies`; miss either and `/` loads on first request but fails on in-app navigation. It does not widen the route-prefix guard, which walks `catalog.Modules`, so `"/"` is exempt from the `/{schema}/` rule module pages follow. `SerginHome` is a plain singleton, not `IOptions<T>`: composed in code, bound to no configuration key, so it follows `SerginUiModuleCatalog`'s precedent rather than `DevUserOptions`'. `UseComponent<T>` constrains to `IComponent, new()` — Blazor instantiates components through `Activator.CreateInstance`, so a component with a primary constructor would fail at first render, and the constraint makes that a compile error instead. And `UseNavItem(label, icon, order)` deliberately takes **no href**: the root's path is fixed by the `@page` template, so an href here could only repeat or contradict it, and a contradiction is a nav entry that 404s with nothing at startup to catch it — `SerginHome.RootPath` is the single value both the builder and `SerginNavMenu` read. `SerginNavMenu` merges the home entry in `OnInitialized` and switches an href of `RootPath` to `NavLinkMatch.All` — under the default `Prefix`, `/` is a prefix of every route and Home would render active on every page.
- **`Sergin.SharedKernel.Infrastracture.WebApi`** *(sic, matches the typo above)* — web-specific infrastructure glue.
- **`Sergin.SharedKernel.Hosts`** — Aspire service defaults (OpenTelemetry, health checks, resilience, service discovery) via `AddServiceDefaults`, plus `SerginCoreExtensions.AddSerginCore<TBuilder>` — the registrations every Sergin host needs regardless of presentation technology: MediatR (scanning every `localModules` entry's `ApplicationAssembly`) + the pipeline behaviors above, the event dispatcher/interceptor, `IDbConnectionFactory`, resolving the scoped `IUserContext` from whatever `IUserContextFactory` the host registered, the localizer, the `module.AddServices(...)` loop over `localModules`, and (new) a `remoteModule.AddRemoteServices(...)` loop over an optional `remoteModules` collection — both guarded together against two modules (local or remote) claiming the same schema. **`AddSerginCore` deliberately does not register an `IUserContextFactory`** — that's the one registration left host-shaped, because the Web API host derives it from `HttpContext` and the Web UI host derives it from configuration. Every host must register its own `IUserContextFactory` *before* calling `AddSerginCore`; both `AddSerginWebApi` and `AddSerginBlazorApp` do this. **There is no dispatch registration here anymore.** `AddSerginCore`'s signature is now `AddSerginCore<TBuilder>(IReadOnlyCollection<ISerginModule> localModules, IReadOnlyCollection<ISerginRemoteModule>? remoteModules = null)` — Local vs. Remote is which collection a module is passed in, not a config key. `Sergin:Dispatch:Modules`, `DispatchModeOptions`/`DispatchModeOptionsValidator`, and `IDispatchRouteResolver`/`ModuleDispatchRouteResolver` are all gone; nothing replaces the config key. A Remote module registers its own `RemoteForwardingHandler<TRequest, TResponse>` (see the `Presentation.Grpc` entry above) per feature via its own `AddRemoteServices`, and MediatR dispatches to it by request type exactly like any other handler — no separate route-resolution step is needed. `ISerginSender`/`RoutingSerginSender` are gone entirely; the Blazor-only replacement, `ISerginDispatcher`/`ScopedSerginDispatcher`, is registered by `AddSerginBlazorKit()` (see the `Presentation.Blazor` entry above), not by `AddSerginCore` — so a future Web API host that calls `AddSerginCore` gets no dispatcher at all, by design, since its endpoints inject `ISender` directly (see Cross-cutting conventions below).
- **`Sergin.SharedKernel.Hosts.WebApi`** (namespace `Microsoft.Extensions.Hosting`) — `SerginWebApiExtensions`: `AddSerginWebApi` adds OpenAPI and `IHttpContextAccessor`, registers `IUserContextFactory` as `InternalUserContextFactory` (the `HttpContext`-derived factory — currently a `SYSTEM`/`ANONYMOUS` stub, real auth not wired), then calls `AddSerginCore`; `UseSerginWebApiAsync` migrates every module (Development environment only), maps each `ISerginWebApiModule`'s endpoints under `MapGroup(module.Schema)`, then maps OpenAPI and (Development-only) Scalar.
- **`Sergin.SharedKernel.Hosts.WebUi`** (namespace `Microsoft.Extensions.Hosting`; `Microsoft.NET.Sdk.Razor` despite holding no `.razor` files itself — see the README for why) — `SerginWebUiExtensions`: `AddSerginBlazorApp` throws immediately outside the Development environment (this host has no real authentication yet — every request runs as one configured user, so it refuses to start anywhere else), then adds Razor Components with interactive server rendering, `AddSerginBlazorKit()`, binds `Sergin:DevUser` to `DevUserOptions` and validates it through `IValidateOptions<DevUserOptions>` (`DevUserOptionsValidator`, registered alongside `.Bind(...).ValidateOnStart()` — a bad key, e.g. an invalid `Permissions` entry, fails startup naming the exact `Sergin:DevUser:*` key and value rather than a generic message), binds `SerginApplicationOptions` the same way (against the **whole** `Sergin` section, since `ApplicationName` is a scalar sitting directly under it; sibling keys with no matching property are ignored), registers `IUserContextFactory` as `ConfiguredUserContextFactory` (builds one `IUserContext` from that configuration), then calls `AddSerginCore` — which today registers no dispatcher at all (see the `Hosts` entry above); the `ISerginDispatcher`/`ScopedSerginDispatcher` a Blazor page actually injects comes from `AddSerginBlazorKit()`, called a few lines above `AddSerginCore` in this same method, not from `AddSerginCore` itself. Then it registers two shell singletons: `SerginUiModuleCatalog` from every `ISerginWebUiModule`, and `SerginHome` from the optional `configureHome` callback (see the `Presentation.Blazor` entry above). `UseSerginWebUiAsync<TRootComponent>` runs a route-prefix guard before anything else: every `IComponent` in every module's `UiAssembly` carrying a `[Route]`/`@page` template must start with `/{module.Schema}/`, because `@page` templates are compile-time constants that `MapGroup(schema)` can't prefix the way it prefixes minimal-API routes — a violation throws at startup, naming the offending component's full type name and template. It then migrates every module (Development only) and maps Razor components with `AddAdditionalAssemblies(catalog.RoutableAssemblies)` plus interactive server render mode.
- **`Sergin.SharedKernel.Modules`** — the module contract every Sergin module implements: `ISerginModule` is the core contract (`Schema`, `ApplicationAssembly`, `ContractsAssembly`, `AddServices`, `MigrateAsync`); `ISerginWebApiModule : ISerginModule` adds only `MapEndpoints`; `ISerginWebUiModule : ISerginModule` adds only `UiAssembly` (the assembly holding the module's routable components — deliberately never `ApplicationAssembly`, which stays UI-free) and `NavItems` (`IReadOnlyCollection<SerginNavItem>`, its nav-menu entries, each an `(Label, Href, Icon, Order)` record). `ApplicationAssembly` is the assembly holding a module's MediatR handlers/repository interfaces/`IUnitOfWork`; `ContractsAssembly` is a separate, thinner assembly (a module's `.Application.Contracts` project) holding only its MediatR command/query request and response records — the shapes a presentation layer actually needs. There is no route-resolver type mapping these assemblies to a schema anymore — `ModuleDispatchRouteResolver` was deleted along with `ISerginSender`/`IDispatchRouteResolver`; MediatR now dispatches purely by request type, whether the handler came from a `localModules` entry's assembly scan or from a `remoteModules` entry's explicit `RemoteForwardingHandler<TRequest, TResponse>` registration (see the `Presentation.Grpc` entry above). A module class implements whichever of the two presentation interfaces match the surfaces it exposes — one class per module implements all its capabilities; which capabilities a given host wires up is that host's choice. This is the seam a host uses to compose modules — see `docs/superpowers/specs/2026-07-26-module-registration-design.md` in the [Sergin.MeterMinder](https://github.com/poursh/Sergin.MeterMinder) repo for the original design rationale (that repo is where the doc lives; it predates this repo's extraction). **`ISerginRemoteModule`** lives here too, alongside `ISerginModule`/`ISerginWebApiModule`/`ISerginWebUiModule`: `Schema`, `ContractsAssembly`, `AddRemoteServices(IServiceCollection, IConfigurationSection)`. Deliberately **not** `: ISerginModule` — a Remote module has no `ApplicationAssembly`/`MigrateAsync` to speak of (no real handlers, no `DbContext`, nothing to migrate), so implementing `ISerginModule` would force a gateway host to pull in everything the module needs to run locally just to reach this one narrow capability. `AddSerginCore` takes `localModules` (`ISerginModule`) and an optional `remoteModules` (`ISerginRemoteModule`) collection — see the `Hosts` entry above. The type implementing `ISerginRemoteModule` must not be the module's `ISerginModule` composition root if that root transitively references the module's `.Application`/`.Infrastructure` — it should live somewhere already isolated from those, e.g. inside the module's own `.Presentation.Grpc.Client` project.
- **`Sergin.SharedKernel.IntegrationTests`** — `SerginWebApiFactory<TEntryPoint>` (`WebApplicationFactory<TEntryPoint>, IAsyncLifetime`, generic over a host's entry point), the shared fixture every module's own integration-test project references. Starts a real `Testcontainers.PostgreSql` container in `InitializeAsync` and sets `Sergin__ConnectionStrings__Database` *before* the host builds (a `ConfigureWebHost` override runs too late for this). Not a test project itself — no `[Fact]`s, just the reusable base. A consumer typically pairs it with its own `[CollectionDefinition]`/`ICollectionFixture<SerginWebApiFactory<Program>>` so every test class in that suite shares one container.

## Value converter template

For a wrapped value object (used by every module's `.Infrastructure.Data` project):
```csharp
internal sealed class FooConverter : ValueConverter<Foo, TPrimitive>
{
    private static readonly ConverterMappingHints defaultHints = new();
    public FooConverter() : this(null) { }
    public FooConverter(ConverterMappingHints? mappingHints)
        : base(x => x.Value, x => new Foo(x), defaultHints.With(mappingHints)) { }
}
```
For a **nullable** wrapped value object, both type params and both conversion expressions get a null ternary instead (`ValueConverter<Foo?, TPrimitive?>`, `x => x == null ? null : x.Value` / `x => x == null ? null : new Foo(x)`).

## Cross-cutting conventions that originate here

- **Results**: `ErrorOr<T>` (global-imported in `.Application`/`.Domain` consumers). `.ToApiResult()` converts to an `IResult`/ProblemDetails. The not-found idiom is bare `Error.NotFound()` — no custom code/description, since `ApiProblemResults` localizes on `error.Code` and every not-found response currently renders identical generic text regardless of aggregate.
- **Permissions**: `[RequiredPermissions("permission.<schema>.<resource>.<action>")]` on a command/query record, enforced by `PermissionCheckPipelineBehavior`. Opt-in per slice — its absence on a consumer's handler is not necessarily an oversight.
- **Blazor pages inject `ISerginDispatcher`, never `ISender`/`IMediator` directly; WebApi endpoints inject `ISender` directly, no wrapper.** This reverses the `2026-08-22` `ISerginSender` move — the dispatcher is Blazor-only again (see the `Presentation.Blazor` entry above), not presentation-agnostic. In Blazor Server, "scoped" is the SignalR circuit's lifetime, not a request's — resolving `ISender` straight off the circuit's `IServiceProvider` would share one `DbContext` for as long as the user's tab stays open, producing an unbounded change tracker, stale first-level-cache reads, and "a second operation was started on this context" the moment two components render in parallel. `ScopedSerginDispatcher.SendAsync` (`Sergin.SharedKernel.Presentation.Blazor/Dispatching`, behind the `ISerginDispatcher` contract in the same folder) opens a fresh `IServiceScope` per call and resolves `ISender` inside it — nothing else. It no longer pre-checks the request's `[RequiredPermissions]` attribute itself, and no longer branches `Local`/`Remote`: both used to be the dispatcher's job when it lived in `Application`/`Infrastructure` as `ISerginSender`/`RoutingSerginSender`, but now both are purely `PermissionCheckPipelineBehavior`'s job inside the MediatR pipeline. That pipeline covers a Remote module's calls too, not just Local ones — `RemoteForwardingHandler<TRequest, TResponse>` (`Sergin.SharedKernel.Presentation.Grpc/Dispatching`, see that project's entry above) wraps a module's `IRemoteInvoker<TRequest, TResponse>` as a real `IRequestHandler`, so `ISender.Send` still routes a Remote request through the same pipeline behaviors a Local handler gets — no second, dispatcher-level check needed. A WebApi request never had the SignalR-circuit problem in the first place — the framework already scopes correctly per request — so an endpoint just resolves `ISender` directly; `Presentation.WebApi` still referencing `Application` today is only for `ListQuery<T>`/`IListQuery<T>` (see that project's entry above), not for a dispatcher.
- **`.razor` files are markup-only; every code-behind line lives in the matching `.razor.cs` `partial class`.** Code written inside an `@code { }` block compiles through the Razor source generator into generated output that the analyzer pipeline (`TreatWarningsAsErrors`, `AnalysisMode=All`, SonarAnalyzer.CSharp) does not see — an unaudited hole in a repo where analyzers otherwise gate every line. `SerginMainLayout.razor`/`.razor.cs`, `SerginNavMenu.razor`/`.razor.cs`, and `SerginProblemPanel.razor`/`.razor.cs` are the reference pairs — none of them has an `@code` block.
- **`SerginMainLayout`'s `<PageTitle>` is a fallback, not the page title.** It renders `SerginApplicationOptions.ApplicationName` so a page that declares no title still gets one, but `HeadOutlet` keeps the *last* title rendered and the body renders after the layout — so every consuming page's own `<PageTitle>` wins. Don't "fix" a page whose tab shows its own name instead of the application name; that is the intended precedence.
- **Module page routes must start with `/{schema}/`.** `UseSerginWebUiAsync`'s route-prefix guard walks every `ISerginWebUiModule.UiAssembly` for `IComponent`s carrying a `[Route]` and throws at startup — naming the offending component and its template — for any route that doesn't start with its own module's schema prefix. Unlike minimal-API endpoints, `@page` templates are compile-time constants, so there is no `MapGroup(schema)` equivalent to prefix them centrally at map time; each component's own `@page` string must already include it.
- **`UseSnakeCaseNamingConvention()`** (via `EFCore.NamingConventions`) maps PascalCase members to snake_case columns — applied per-module in each consumer's `DbContext`, not here, but the package reference lives in this repo's `Directory.Packages.props`.
- **Local variable typing**: declare a local as the narrowest interface its actual usage needs (e.g. `IReadOnlyCollection<T>` over `List<T>` when only ever handed to something expecting that interface). Collection expressions (`[.. ...]`) can target an interface directly since C# 12.

Each consuming project has a `GlobalUsings.cs`; check it before adding `using` statements that may already be global.
